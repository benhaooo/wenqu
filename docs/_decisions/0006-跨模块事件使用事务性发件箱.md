# 0006 跨模块事件使用事务性发件箱

- 日期：2026-10-10
- 状态：已采纳

## 背景

模块依赖是单向的，上游模块状态变化需要通知下游时（文档内容变更后重新索引、文档删除后删除文本块、上传文件后开始解析）使用事件。要求：

- 业务数据写入成功，事件就一定会被处理；业务回滚，事件就不能发出。
- 服务在任意时刻崩溃重启后，未处理的任务能继续完成。
- 「停止编辑 30 秒后重新索引」这类延迟触发同样不能因为重启而丢失。

## 备选方案

1. **Spring `ApplicationEvent` + `@EventListener`**：监听器在事务内同步执行，事务回滚时副作用已经发生；不跨进程，崩溃即丢失。
2. **`@TransactionalEventListener(AFTER_COMMIT)` 中发送 MQ 消息**：解决了回滚问题，但事务提交后、消息发出前崩溃，事件丢失，文档内容已改而索引永远是旧的。
3. **事务中直接发送 MQ 消息**：消息发出后事务回滚，下游处理不存在的数据；MQ 不可用时业务写入失败。
4. **事务性发件箱（Outbox）**：在业务事务中把事件写入发件箱表，转发器轮询发件箱，把事件投递到 RabbitMQ，收到确认后标记为已发送。

## 决定

采用事务性发件箱：

- 发件箱表在 `infra` schema，由 `infra` 提供写入接口，业务模块在自己的 service 事务中调用。
- 转发器使用 `select ... for update skip locked` 批量读取到期事件，多实例部署时不重复投递；投递使用 RabbitMQ 发布确认。
- 事件带 `available_at`，用于延迟触发。编辑器保存时写入 `available_at = now() + 30s` 的重新索引事件，同一文档未投递的重新索引事件合并为一条，实现可持久化的防抖。
- 消费者按「至少一次」处理，必须幂等（例如重新索引先删除该文档的旧文本块再写入）。
- 文档删除与文本块删除之间存在投递延迟，检索时额外以 `document` 模块提供的有效文档集合过滤，保证已删除文档不会出现在回答中。

## 代价

- 事件不是实时投递，有轮询间隔级别的延迟（秒级）。
- 发件箱表需要定期清理已发送的记录。
- 消费者必须幂等，所有消费逻辑都要按这个前提设计和测试。
