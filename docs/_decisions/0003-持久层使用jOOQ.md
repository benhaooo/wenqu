# 0003 持久层使用 jOOQ

- 日期：2026-10-10
- 状态：已采纳

## 背景

需求文档给出的持久层选项是 MyBatis-Plus 或 Spring Data JPA，二选一后全项目统一。本项目大量使用 PostgreSQL 特有能力：递归 CTE（目录树、回收站级联）、pgvector 距离运算、全文检索、`FOR UPDATE SKIP LOCKED`（发件箱转发）、`jsonb`。同时项目要求模块不能访问其他模块的表，并希望由工具强制。

## 备选方案

1. **MyBatis-Plus**：
   - 优点：国内使用广泛；SQL 完全可控；单表 CRUD 省代码。
   - 缺点：SQL 写在 XML 或注解字符串中，表名、列名错误只能在运行时发现；表与代码之间没有编译期关联，难以用工具检查「模块只访问自己的表」。
2. **Spring Data JPA**：
   - 优点：实体映射与派生查询省代码。
   - 缺点：递归 CTE、向量检索、全文检索都要写 native query，失去类型安全；需要关闭 `ddl-auto` 并与 Flyway 保持实体一致；懒加载、脏检查等隐式行为增加排查成本。
3. **jOOQ**：
   - 优点：类型安全的 SQL DSL，能表达 PostgreSQL 的高级特性；代码从 Flyway 迁移后的真实表结构生成，表或列不存在时编译失败；生成类按 schema 分包，可以用 ArchUnit 限制每个 schema 只能被所属模块的 `repository` 引用。
   - 缺点：编译时需要数据库（使用 Testcontainers 解决）；简单 CRUD 比 MyBatis-Plus 多写几行；pgvector 的 `vector` 类型需要自定义 Binding。

## 决定

使用 jOOQ（开源版，支持 PostgreSQL），偏离需求文档中的二选一。

构建流程：Maven `generate-sources` 阶段用 Testcontainers 启动与运行时相同镜像的 PostgreSQL → Flyway 执行迁移 → jOOQ 生成代码到 `target/generated-sources/jooq`。迁移脚本是表结构的唯一来源。

## 代价

- 后端编译依赖 Docker，没有 Docker 的环境无法编译。CI 运行器自带 Docker。
- 每次完整构建会启动一个临时 PostgreSQL 容器，增加数秒构建时间。
- 团队成员需要熟悉 jOOQ DSL。
- 需求文档的技术栈表需同步修改为 jOOQ。
