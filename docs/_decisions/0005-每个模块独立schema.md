# 0005 每个模块独立 schema

- 日期：2026-10-10
- 状态：已采纳

## 背景

后端是按业务领域划分模块的单体应用，规则要求模块之间只能通过对方的 service 接口调用，不能访问对方的表。如果所有表都在同一个 schema 中，这条规则只能靠约定和代码审查维持。

## 备选方案

1. **单个 `public` schema，表名加模块前缀**：简单；但 jOOQ 生成类都在同一个包中，无法按包区分归属。
2. **每个模块一个 schema，单个 Flyway 实例管理**：jOOQ 按 schema 生成到 `com.wenqu.jooq.<schema>`，ArchUnit 可以限制每个包只能被所属模块的 `repository` 引用；迁移脚本按模块分目录，版本号全局唯一。
3. **每个模块一个 schema，每个模块一个 Flyway 实例**：迁移历史彻底隔离；但需要自定义 Flyway 配置和执行顺序，个人项目收益不大。
4. **每个模块一个数据库**：隔离最彻底，但失去事务一致性，向量检索无法与业务过滤结合。

## 决定

采用方案 2：

- schema 名与模块名相同，Flyway 按配置创建 schema，历史表在 `public`。
- 迁移脚本放在 `db/migration/<模块>/`。
- 跨 schema 不建外键、不做 join。PostgreSQL 在技术上允许跨 schema join，不做是为了守住模块边界。
- 需要按空间、文档过滤的表冗余存储 `workspace_id`、`document_id`。例如 `retrieval` 的文本块表冗余这两个字段，检索时由 `document` 模块的 `api` 提供允许的文档 id 集合，以 `document_id = any(?)` 作为过滤条件。
- 文本块检索使用 HNSW 索引时开启 `hnsw.iterative_scan`：HNSW 先取近邻再应用过滤条件，过滤条件严格（例如只查一个文件夹）时返回结果可能少于期望数量，迭代扫描会继续扫描直到满足数量。

## 代价

- 冗余字段需要在源数据变化时同步（例如文档移动到其他空间）。本项目文档不跨空间移动，`document_id` 不变。
- 允许的文档 id 集合以数组参数传入，几千个文档以内性能可接受；规模更大时需要改为在检索 SQL 中关联权限数据，打破 schema 边界，需重新决策。
- 失去数据库层的外键保护，引用完整性由应用通过领域事件维护（例如文档删除后删除文本块）。
