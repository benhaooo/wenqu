# 0001 向量存储选择 pgvector

- 日期：2026-10-10
- 状态：已采纳

## 背景

AI 问答需要对文档切块后的向量做相似度检索。目标规模是 5～20 人团队，文本块在万级到十万级。检索需要结合业务条件过滤（空间、文件夹、文档、权限），删除文档时向量必须同步删除。

## 备选方案

1. **pgvector（PostgreSQL 扩展）**：向量与业务数据在同一个库。
   - 优点：可以和业务数据在同一事务中写入和删除；过滤条件直接写在 SQL 的 `WHERE` 中；少运维一个组件；备份恢复一体；支持 HNSW 索引。
   - 缺点：千万级以上数据量和高并发下性能不如专用向量库；带过滤条件的近似检索需要处理召回不足的问题。
2. **Milvus / Qdrant 等专用向量库**：
   - 优点：大规模下检索性能好，过滤与分片能力强。
   - 缺点：多一个有状态组件；业务数据与向量之间需要做最终一致性同步，删除文档后向量残留会导致回答引用已删除内容。
3. **Elasticsearch / OpenSearch 向量检索**：
   - 优点：全文检索与向量检索在同一个引擎，适合混合检索。
   - 缺点：资源占用大；同样存在跨存储一致性问题；本项目全文检索可以由 PostgreSQL 承担。

## 决定

使用 pgvector，向量与业务数据放在同一个 PostgreSQL 16 库中，使用 HNSW 索引和余弦距离。

## 代价

- 数据量达到百万级以上、或检索并发很高时需要重新评估，届时迁移到专用向量库。检索逻辑集中在 `retrieval` 模块，迁移范围可控。
- HNSW 带 `WHERE` 过滤时先取近邻再过滤，过滤条件严格时返回结果可能少于期望数量，需要开启 pgvector 的迭代扫描（`hnsw.iterative_scan`），见 [0005](0005-每个模块独立schema.md)。
- 向量写入会占用业务库的 IO 和内存，需要在压测中关注。
