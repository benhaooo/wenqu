# 0002 协同服务使用 Node 独立部署

- 日期：2026-10-10
- 状态：已采纳

## 背景

多人实时协同编辑基于 Yjs（CRDT）。服务端需要维护每篇文档的 Yjs 文档状态、处理 WebSocket 连接、广播增量更新和光标感知信息。主后端是 Java（Spring Boot）。

## 备选方案

1. **独立 Node 服务，使用 Hocuspocus**：
   - 优点：Yjs 是 JavaScript 原生实现，Hocuspocus 是 Tiptap 官方的 Yjs 服务端，鉴权、持久化、感知等扩展点完整；与前端使用同一份 Yjs 实现，没有跨语言编码兼容问题；长连接负载与 Java 后端隔离，可以单独扩容。
   - 缺点：多一个服务和一门运行时；鉴权和持久化需要回调 Java 后端。
2. **在 Java 后端内实现 Yjs 同步**：使用 y-crdt 的 Java 移植或 JNI 绑定（yrs）。
   - 优点：只有一个后端服务。
   - 缺点：Java 生态的 Yjs 实现成熟度低，协议细节（同步、感知、子文档）需要自己实现；大量长连接与业务请求争用同一进程资源。
3. **使用托管协同服务**（如 Liveblocks、Tiptap Cloud）：
   - 优点：无需自建。
   - 缺点：文档内容存放在第三方，不符合团队知识库的数据归属要求；有费用。

## 决定

协同服务是独立的 Node 服务（`collab/`，Hocuspocus），只负责实时同步，不包含业务逻辑：

- 连接鉴权：校验 Java 后端签发的 JWT，并调用后端接口确认用户对文档的权限。
- 持久化：定期回调 Java 后端保存 Yjs 状态，由后端更新文档内容并触发重新索引。

## 代价

- 部署和本地开发多一个服务，需要处理服务之间的鉴权（服务间调用使用独立密钥）。
- 权限变更需要通知协同服务断开或降级已有连接。
- 文档内容的权威来源是 Java 后端的数据库，协同服务的内存状态丢失时从后端重新加载。
